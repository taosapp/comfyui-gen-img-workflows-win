# 图片风格转换：性能剖析与优化建议

实测时间 2026-09-28 ｜ 机器 RTX 3060 12GB + 32GB RAM ｜ 启动参数 `--lowvram --preview-method auto`
被测工作流 `workflows/图片风格转换.json`（Qwen-Image-2.1 GGUF Q5_K_M + qwen3vl_8b_int8 文本编码器）
素材 `input/style_test_scene.png`（1024×1024）与 `input/1.jpg`，`resolution=1024`，euler-beta / seed 424242

> 所有数字均为**同机实测**，非估算。测量方法见文末附录。

---

## 1. 结论先讲

**每张图的瓶颈是采样阶段的计算量，不是文本编码器。** 采样窗口内 GPU 利用率中位 99%、功耗 135–160W（3060 上限约 170W）、显存带宽利用率仅 35% —— 是**算力打满型**瓶颈，不是搬运受限。所以出路只有「少做事」：**缓存前缀、减步数、降分辨率**，换更小的量化权重不会更快。

| 优化 | 实测收益 | 质量代价 | 状态 |
| --- | --- | --- | --- |
| ① `QwenImage21Cache` 前缀缓存 | **总时长 −37%** | **零**（逐像素一致） | ✅ **已装进工作流** |
| ② 步数 20 → 12 | 采样 −42% | 放大对照下肉眼无差别 | ⬜ 改一个数字即可 |
| ③ `resolution` 1024 → 768 | −52% | 出图变小（1024×576） | ⬜ 按用途取舍 |
| ④ Viggle turbo 蒸馏 LoRA（6 步） | **采样 183s → 26s（约 7×）** | **大**：失去负向提示词 + LoRA 部分失效 | ⚠️ 不建议直接用，见 §5 |

## 2. 耗时构成（实测）

| 变体 | 采样阶段 | 总耗时 |
| --- | --- | --- |
| 20 步 + cfg3.5，**无缓存** | 302 s（15.1 s/it） | 305 s |
| 20 步 + cfg3.5，**有缓存** | 182 s（9.1 s/it） | **193–198 s** |
| **12 步 + 有缓存** | 107 s | **119 s** |
| turbo LoRA 6 步无 CFG + 有缓存 | 26 s | **34 s** |
| 8 步 + 有缓存 | 72 s | 85 s |

- 每步的 UNet 调用成本基本恒定（**约 4.6 s/次**）。cfg 3.5 时每步算 2 次（正/负向），所以 20 步 = 40 次调用 ≈ 183 s；turbo 无 CFG 每步 1 次，6 步 = 6 次调用 ≈ 27 s。**加速的本质是调用次数变少**。
- 非采样开销：文本编码 ≈ 14 s（热态）＋ VAE 解码与节点杂项 ≈ 10 s。
- **重启后第一张额外 +160 s**：文本编码器 8.9 GB 读盘约 100 s + GGUF UNet 首次加载 64 s。同进程内后续只走内存重上台。
- **12 GB 卡上模型永远在换进换出**：文本编码器 8.9 GB + UNet 5.1 GB = 14.5 GB > 12 GB，且模型一被卸载，ComfyUI 会把依赖它的缓存节点一并作废，所以文本编码几乎每张图都要重跑。

## 3. 关于文本编码器（回答「是否过大」）

`qwen3vl_8b_int8_convrot.safetensors` = **9.35 GB**（运行期 staged 8916 MB）。

- **确实偏大**：它 + UNet 在 12 GB 卡上不可能共存，每张图都要把 8.9 GB 搬上搬下。
- **但它不是瓶颈**：热态两趟合计仅 14.2 s，约占单张总时长 6%。缩它换来的提速微乎其微。
- **也不要为省显存换 GGUF 版文本编码器**（约 5 GB）：文本编码器对量化最敏感，质量风险远大于这点收益。
- 它为什么不能省：`TextEncodeQwenImage21` 把参考图送进视觉塔（1024² 图 ≈ 1024 个视觉 token），因果注意力下**文本 token 会读到图像 token**，这段计算是真在起作用，砍不掉。

## 4. 已落地：`QwenImage21Cache`（前缀 KV 缓存）

**已接入 `workflows/图片风格转换.json`**，接法 `UnetLoaderGGUF → QwenImage21Cache → KSampler.model`，参数 `device=auto` / `dtype=default`。画布上节点标题为「KV 缓存加速（勿删）」。

- 作用：把「文本 + 参考图」这段与采样步无关的前缀 K/V 缓存下来，第 2 步起不再重算。**该功能默认是关的**（`prefix_cache_enabled=False`，`comfy/ldm/qwen_image21/model.py:234`），必须显式挂节点才生效。
- **实测收益：总时长 −37%，采样阶段 −40%**（182 s vs 302 s，单变量对照、可复现）。
- **质量零损失**：`dtype=default` 是无损存储。加与不加输出逐像素一致（最大差 0）。改动史在 git 里，不再另存 `.bak`（原来那份备份已删）。
- 回退：把节点 `device` 改成 `off` 即等于关闭（不必删节点）。

## 5. 步数与分辨率：最安全的两个杠杆

### 步数扫描（同图、同种子、同提示词，均有缓存）

| 步数 | 采样 | 总耗时 | 相对 20 步 | 与 20 步结果的像素差 |
| --- | --- | --- | --- | --- |
| 20 | 183 s | 219 s | 基线 | — |
| 15 | 136 s | 209 s | −26% | 大（细节不同） |
| **12** | **107 s** | **119 s** | **−42%** | 大（细节不同） |
| 10 | 88 s | 101 s | −52% | 开始偏暗 |
| 8 | 72 s | 85 s | −61% | 明显偏暗、纹理变糊 |

**像素差不等于质量差**——扩散模型步数不同，细节必然不同。真正要看的是 `output/stepsweep_zoom.png`（整图 + 中心放大）：**20 / 15 / 12 步肉眼无差别；10 步开始偏暗；8 步明显走样**。社区结论也一致：Qwen-Image-2.1 基线 40 步没有必要，12–25 步都可用。

> 想改只需在画布上把 KSampler 的 `steps` 从 20 改成 12。本文件不改它，因为这是质量取舍，且单图单种子的结论宜多测几张再定。

### 分辨率

`TextEncodeQwenImage21` 的 `resolution` 同时决定参考图缩放与目标画布。1024 → 768 时 1376×768 变 1024×576，时间约腰斩（−52%）。

## 6. Viggle turbo 蒸馏 LoRA：快 7 倍，但不是即插即用（未采纳）

**实测（6 步，官方 sigma 序列，本机 GGUF 模型）**：采样 183 s → **26 s**（缓存开）/ 43 s（缓存关），总时长 219 s → **34 s**。

但有三道坎，所以**没有**把它接进工作流：

1. **失去负向提示词**。turbo 必须走 `BasicGuider`（无 CFG），而当前工作流的「暗调、低对比水彩」质感主要来自负向提示词（"overexposed, washed out, high key lighting, low contrast"）。实测对照（`output/turbo_vs_baseline.png`）：基线是暗调，turbo 变成明亮晴天——**构图保留、氛围完全变了**。要保风格就得重写正向提示词。
2. **LoRA 在 GGUF 上部分失效**。日志报 96 个 `lora key not loaded`，全部集中在 `img_mlp.gate_up`（32 层 × 3 种键）——GGUF 把 gate/up 融合成了单一层，键名对不上。而 `img_mlp` 恰是该蒸馏的**核心训练目标**之一。官方与转换作者都要求用 **bf16 / int8 的 DiT**（`qwen_image_2.1_bf16.safetensors` 14.2 GB 或 `qwen_image_2.1_int8_convrot.safetensors` 7.3 GB），即还要再下 7–14 GB 权重。
3. **许可证**。Qwen Research License，仅限非商业研究/评估。若项目要开源或商用，这条路走不通。

已下载并校验的文件（SHA256 通过）在 `models/loras/qwen_image_2.1_viggle_turbo_v0.2.1_r128_comfy.safetensors`（840 MB）。若要走这条路，还需：下 int8 DiT → 重构工作流为 `ManualSigmas + BasicGuider + SamplerCustomAdvanced` → 重调提示词。好消息是所需节点本机**全部原生具备**（`ManualSigmas` / `BasicGuider` / `KSamplerSelect` / `RandomNoise` / `LoraLoaderBypassModelOnly`），无需装第三方节点。

sigma 序列（6 步，按 latent 尺寸自适应；1024 分辨率时 x≈2.0）：

```
基准 [1, .9375, .875, .75, .5, .25, 0]，s(t) = x·t/(1+(x−1)·t)，x = e^(0.5 + 0.4·(latent_H·W−256)/7936)
1024² 参考图 → latent 64×64 → x = 2.0008 → 1.0, 0.96775, 0.93336, 0.85719, 0.66676, 0.40010, 0.0
```

## 7. 顺带确认的环境事实

1. **`--lowvram` 在这台机器上不生效**。`comfy-aimdo 0.5.5` 已装，启动日志有 `DynamicVRAM support detected and enabled`，该参数被忽略，文本编码器也**没有**被丢到 CPU。
2. **别频繁重启**：重启后第一张要多付约 160 s 冷加载。
3. ComfyUI 按输入哈希缓存节点结果，但**模型被卸载会让依赖它的缓存一起失效**——12 GB 卡上模型常驻不了，所以文本编码几乎每张都重跑。
4. 下载 HF 大文件：直连 hf-mirror 时 302 会跳到 `cas-bridge.xethub.hf.co`（被墙，0 字节）；经代理 `http://10.10.100.199:3128` 则跳到 `us.aws.cdn.hf.co`（可用，8 线程约 10 MB/s）。**Python 的 urllib 走这条 CDN 会被拒**，用 curl。

## 附：测量方法（可复现）

工具都在 `scripts/legacy/`（已纳入 git）：

| 脚本 | 用途 |
| --- | --- |
| `run_workflow_json.py` | 前端工作流 JSON → API prompt 并提交执行（无头验证工作流能否真跑通） |
| `submit_api.py` | 直接提交一张 API 格式的图 |
| `step_sweep.py` | 步数扫描：耗时 + 像素差 + 拼对照图 |
| `perf_probe.py` | 变体裁剪法定位阶段耗时 |
| `metrics_ink.py` | 彩墨保真度五指标（结构/色距/纹理/饱和/明度） |
| `hf_download.sh` | 走代理下载 HF 大文件（hf-mirror 会被墙） |
| `hf_download.sh` | curl 分块并行下载 + SHA256 校验（`PROXY=` 走代理） |

要点与坑：

1. 另起实例落盘日志：`python main.py --lowvram --preview-method auto --disable-auto-launch --verbose INFO <日志>`
2. ComfyUI 不打印节点级耗时，用**变体裁剪法**从外部拆；采样阶段耗时可直接读日志 tqdm 尾行的累计墙钟。
3. **A/B 必须改动一个无关输入（如换 seed）逼缓存失效**，否则复跑同一张图是 0.02 秒的缓存命中。
4. 首次运行混入冷加载（约 +160 s），先热一轮再测。
5. 后台 `nvidia-smi` 每 2 s 采样取中位数，判断是算力受限还是带宽受限。
